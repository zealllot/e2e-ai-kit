# PRD 0001 — e2e-ai-kit v0.2: contracts + lints + CLI

> Status: ready-for-agent. Scope confirmed 2026-05-18 during the
> grilling session that produced [`../../CONTEXT.md`](../../CONTEXT.md)
> and the v0.1 surface.

## Problem Statement

The kit shipped at v0.1 with three contract stubs
([`contracts/case-schema.md`](../../contracts/case-schema.md),
[`contracts/app-context-schema.md`](../../contracts/app-context-schema.md),
[`contracts/slot-contract.md`](../../contracts/slot-contract.md)).
Their design intent is captured in
[`CONTEXT.md`](../../CONTEXT.md), but the artifacts substrates produce
under those contracts have no mechanical way to be verified. As a
result:

- Reviewers can flip `status: approved` on a case without filling
  `reviewer_checked`. The risk triple "rubber-stamp case approval" has
  no executable mitigation.
- Manual edits to generated permission tables, substrate-business-name
  drift into the framework slot, and Tier-classification duplication
  between slot and `skills/maintenance/SKILL.md` can all land in PRs
  unnoticed.
- The 5-stage onboarding flow ([`../ONBOARDING.md`](../ONBOARDING.md))
  gates each phase on "must pass lint" — but the lints do not exist.
- Every contract change is communicated verbally because there is no
  executable specification of the contract.
- Distribution (initially vendor copy, eventually npm) cannot start
  without a `package.json` and a CLI entry point.

A substrate operator today has all the design but none of the
enforcement.

## Solution

Ship kit v0.2 with three concrete contracts and three CI-enforceable
lints, fronted by a CLI:

- Each contract document is rewritten from stub into a full,
  unambiguous specification of frontmatter, body sections, source-type
  semantics, and prohibited content (as applicable per artifact kind).
- One lint per contract reads the relevant substrate artifact, applies
  the contract rules via three central **registries** (the single source
  of truth for which fields/sections/items are required), and exits
  non-zero on any violation.
- A CLI wrapper (`e2e-ai-kit lint <case | app-context | slot> [files...]`)
  is the user-facing entry point and the CI integration point.
- A `package.json` makes the kit installable as a vendored dependency
  in substrates. Publishing to npm is **deferred** to v0.3+; first
  substrate (mcd-website) onboards v0.2 by direct file copy.

After v0.2, the kit is *enforceable* on a substrate, which is the
prerequisite for the substrate-side cleanup PRD and for the
second-substrate onboarding that will validate Portability.

## User Stories

### As a substrate operator (the kit's primary day-to-day user)

1. As a substrate operator, I want CI to reject case `.md` files with
   `status: approved` but an empty `reviewer_checked` array, so that
   rubber-stamp approvals are mechanically blocked.

   required body sections, so that a `state-machine` case cannot ship
   without a "State machine" section.

   `reviewer_checked` item is in the closed enum for that `case_type`,
   so that reviewers cannot record arbitrary strings.
5. As a substrate operator, I want `app-context-lint` to enforce that
   all 10 required sections are present with their `<!-- source: ... -->`
   markers, so that the substrate's Application Context Document is
   structurally complete.
6. As a substrate operator, I want `app-context-lint` to require
   `last_verified_by_human` on every `source: probe+human` section, so
   that probe-generated drafts cannot be trusted without a human
   signature.
7. As a substrate operator, I want `skill-slot-lint` to enforce that
   the slot covers all S1-S9 sections, so that an incomplete slot cannot
   advance the substrate past Phase 1 of onboarding.
8. As a substrate operator, I want `skill-slot-lint` to flag any
   Tier-1/2/3 classification content inside the slot, so that the
   cross-framework authority (`skills/maintenance/SKILL.md`) remains
   the single source of truth.
9. As a substrate operator, I want `skill-slot-lint` to flag
   substrate-business-name patterns in the slot, so that substrate
   concerns do not leak into the portable framework slot.
10. As a substrate operator, I want a local CLI
    (`npx e2e-ai-kit lint <kind>`), so that I can verify artifacts
    before pushing a PR.
11. As a CI configurator, I want each lint to return a non-zero exit
    code on failure, so that GitHub Actions can use the lints as
    required checks.
12. As a substrate operator, I want lint output to point at the
    specific file + line + violated rule id, so that fixing failures is
    fast and unambiguous.
13. As a substrate operator, I want each rule id to map to a section in
    the contract docs, so that "why is this an error?" is one click
    away from "what does the contract say?"

## Implementation Decisions

### Modules

Six modules are introduced; four are **deep** (testable in isolation,
stable interfaces) and two are **shallow** (composition + IO):

| # | Module | Depth | Public interface (prose) |
|---|---|---|---|
| 1 | Frontmatter parser | deep | `parseFrontmatter(input)` returns `{ meta: object, body: string }`. Accepts raw markdown string; throws on malformed YAML. No file IO. |
| 2 | Section walker | deep | `walkSections(body)` returns `Section[]` where each `Section` has `{ title, level, content, metadata }`. `metadata` parses `<!-- source: probe, last_probed: 2026-05-18 -->`-style HTML comments inside each section. |
| 3 | Three registries (case-type, app-context-section, slot-section) | deep | Each registry exposes lookup functions returning required-fields / required-sections / closed-enum lists. Pure data + small functions; no IO. Adding a new `case_type` or section is a one-line registry change + a contract-doc + CONTEXT.md update, all in one PR. |
| 4 | Lint runner | medium | `runLint(filepath, registry)` composes (1) + (2) + (3) and returns `LintResult { ok, errors, warnings }` where each `LintError` has `{ file, line?, section?, ruleId, message }`. |
| 5 | Result formatter | shallow | Renders `LintResult` to terminal output (with color, file:line) **and** GitHub Actions annotation format (`::error file=...,line=...::message`). Output mode toggled by env var. |
| 6 | CLI | shallow | `e2e-ai-kit lint <case \| app-context \| slot> [files...]`. Defaults to glob per kind when no files specified. Dispatches to the right registry; uses the formatter; exit code is 1 on any error. |

### Architectural decisions

- **TypeScript with strict mode**, no transpile-time dependency on
  Playwright/Cypress/qor. The kit is framework-agnostic; framework
  bindings stay in substrate slots.
- **Distribution v0.2**: vendor copy. Substrates clone or `git
  submodule` the kit, or copy directories during onboarding (Phase 0).
  npm publish is **deferred to v0.3+** to avoid premature versioning
  commitments before substrate #2 validates the contracts.
- **Package layout**: `package.json` with `bin: { "e2e-ai-kit": "..." }`
  so `npx e2e-ai-kit lint ...` works from a substrate that vendored
  the kit as a path dependency.
- **File discovery**: lints accept explicit file paths OR a glob
  default per kind (`tests/cases/*.md` for case-lint;
  `tests/app.context.md` for app-context-lint;
  `.claude/skills/*/SKILL.md` for skill-slot-lint).
- **Exit codes**: any error → exit 1. Warnings → exit 0 + stderr
  output. No partial-success exit codes (CI gates need a binary
  signal).
- **Error model**: each `LintError` carries a `ruleId` that maps to an
  anchor in the relevant contract doc (e.g. `case.frontmatter.approved_by_required`,
  `slot.forbidden.tier_classification`). The formatter's output
  includes both the error and the anchor link so the operator can
  navigate to the governing rule.
- **No code generation**: the contracts are hand-written prose; the
  registries are hand-written TypeScript. A future iteration may apply
  the SoT-Doc-DriftCheck triplet (Product component 4) to *the
  contracts themselves* — registry as SoT, contract doc as generated.
  Deferred to v0.3+.

### Schema choices

- **Case schema**: YAML frontmatter in each `tests/cases/*.md` file
  (already conventional). Body sections enforced per `case_type`
  (closed enum: `happy-path`, `state-machine`, `reference`, `family`,
  `save-flow`). `reviewer_checked` is a list whose allowed values are
  per-`case_type`.
- **Application Context schema**: YAML frontmatter on the single
  `tests/app.context.md` file + 10 required sections (1 optional)
  each marked by an HTML comment `<!-- source: human | probe |
  probe+human -->` plus optional freshness metadata. Sections without
  a `source:` marker are an error.
- **Slot contract**: YAML frontmatter on `SKILL.md` with required
  `framework` / `admin_stack` / `required_sections` fields + 9
  required sections (S1-S9). Forbidden content is enforced by a list
  of patterns: presence of "Tier 1/2/3" phrasing, mention of any item
  in a per-substrate `substrate_business_terms` list (configured by
  the substrate, not the kit).

### API contracts (between modules)

- `parseFrontmatter` → `{ meta, body }`. `meta` is untyped at parser
  level; typing happens in lints via the registry.
- `walkSections` → `Section[]` ordered by document order. `metadata`
  on each section is `Record<string, string>`; absence is `{}`.
- Each registry exports a lookup function and a list-all function.
  `getCaseType('happy-path')` returns the spec; `listCaseTypes()`
  returns all known kinds.
- `runLint` is pure given `(filepath, registry)`. Filesystem reads are
  scoped inside the lint runner; parsers and registries do no IO.
- CLI is the only module allowed to touch `process.exit`, `process.env`,
  and `console`.

## Testing Decisions

### What makes a good test

- Test **external behavior**, not implementation details. The
  registries' tests should assert "given `happy-path`, returns this
  required field list," not "registry uses this internal Map." Lint
  tests should assert "this fixture file produces this set of `ruleId`s,"
  not "the lint function called the walker twice."
- Tests must not require network, database, browser, or any
  filesystem layout outside the test's own `fixtures/` directory.
- All tests should run in milliseconds; the kit's test suite must be
  fast enough to run pre-merge on every PR.
- A failing test must produce a message that names the rule or
  invariant being violated; "expected true, got false" is unacceptable.

### Which modules are tested

Per scope confirmation:

1. **Frontmatter parser**: malformed YAML, missing frontmatter, edge
   cases (`---` appearing inside body, multi-line YAML strings, empty
   frontmatter, very large bodies). Pure-function tests; no fixtures
   on disk.
2. **Section walker**: section depth, missing sections, malformed
   metadata comments (`<!-- source: ... -->` with bad syntax), mixed
   sections with and without metadata, sections with HTML in body.
   Pure-function tests against string inputs.
3. **Three registries**: every closed-enum kind returns the expected
   shape; unknown kind throws; the list-all function returns the same
   set as a hand-coded reference. These tests **pin the registries** so
   that changes to the closed enums break the test, forcing reviewers
   to update both the registry and the contract doc in the same PR.
4. **Lint integration tests**: per lint, a `fixtures/good/` directory
   of files that MUST pass and a `fixtures/bad/<rule>/` structure where
   each subdirectory targets exactly one `ruleId`. Tests assert that
   `runLint` returns `ok: true` for good files and `errors[0].ruleId
   === <expected>` for bad files. Golden-fixture style.

### Prior art

- No prior art in this repo (greenfield). Looking at the broader
  ecosystem:
  - **ESLint's RuleTester** uses inline code-as-string fixtures with
    expected error annotations. Cleaner than file-on-disk for some
    use cases, but our lints read whole files (with frontmatter +
    multi-section body), so file fixtures are simpler.
  - **Prettier** and **dprint** use directory-based snapshot fixtures.
    This matches our case-lint and app-context-lint structure.
  - **Biome** publishes JSON schemas alongside its lints for IDE
    integration; we may copy this approach in v0.3+.

We pick **directory-based fixtures**: each lint has its own
`__tests__/fixtures/{good,bad}/` tree, one file per scenario, with the
`ruleId` encoded in the filename or directory name. This minimizes the
test framework's role (any test runner can walk a directory and assert
exit code or returned object).

## Further Notes

- v0.2 is **internal preview**. No backwards-compatibility commitment
  until v1.0. v1.0 requires Phase 5 validation: a second substrate
  completes `docs/ONBOARDING.md` end-to-end. Until then every contract
  is provisional.
- The three registries are the closest thing to a *machine-readable
  spec* the contracts have, **and** they are the single source of
  truth for what each lint enforces. If the registries diverge from
  CONTEXT.md or the contract docs, both files must be updated in the
  same PR. This Product convention should be documented in
  CONTEXT.md after v0.2 ships (anticipated v0.3 add).
- The "ready-for-agent" label on this issue indicates an AFK agent can
  pick it up. The agent should:
  - Read [`CONTEXT.md`](../../CONTEXT.md) before touching the
    registries; the registries must remain consistent with the
    glossary.
  - Read [`docs/WORKFLOW.md`](../WORKFLOW.md) for the operating model
    that the lints enforce.
  - Read [`docs/adr/0001-product-substrate-output.md`](../adr/0001-product-substrate-output.md)
    before touching the slot lint; the slot's forbidden-content
    invariants are load-bearing for the B2 design.
  - Read [`docs/adr/0002-extract-to-separate-repo.md`](../adr/0002-extract-to-separate-repo.md)
    before changing `package.json` distribution semantics.
- Each lint's `ruleId` namespace is part of the public surface (CI
  integrations, editor extensions in the future may reference them).
  Treat `ruleId` strings as durable identifiers; renames are breaking
  changes.
- Tests for the three registries are **the strongest defense against
  silent contract drift**. They should be the most thoroughly written
  tests in the suite.
